# Redesign acceptance traceability

This matrix maps the redesign's required acceptance flows to repository tests. Automated coverage exercises local Laravel, PostgreSQL, and Docker boundaries with test databases and synthetic identities. It does not establish live Firebase configuration, email delivery, Render deployment behavior, or physical-device operation.

## Additional required security boundaries

- CSRF: `CloudCsrfProtectionTest` runs Cloud browser mutations with Laravel's production CSRF middleware enabled; missing tokens return 419 and a matching session token proceeds.
- Authorization and IDOR: event, gate, ticket, manager, and staff feature tests reject cross-event or unassigned access.
- Replay and expiry: ticket transfer, guest redemption, checkout idempotency, manager invitation, email completion, and one-use Node pairing tests cover stale and replayed credentials.
- Malformed input: Firebase session, pairing code, QR payload, snapshot package, registration identity, and checkout validation tests cover invalid data.
- Logging: PDF, verification-email, Node Docker, and sensitive-response tests check generic failures and secret/credential redaction.
- Concurrency: `api/scripts/verify_pgsql_concurrency.php` uses separate PostgreSQL processes and barriers for races that SQLite feature tests cannot establish.

## Verification boundary

Automated tests use generated keys, fake external identity responses, and isolated databases. They do not prove that Firebase is configured, that an email provider delivers messages, that Render is running the latest release, or that phone cameras, venue Wi-Fi, printer output, and real WAN loss behave correctly. The project owner must run those physical and live-service checks using [`physical-device-test-plan.md`](physical-device-test-plan.md). A healthy `/up` response alone is not operational acceptance.
